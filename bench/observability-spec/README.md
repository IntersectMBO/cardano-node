# Cardano node performance observability: specification

**Status:** draft 0.1 (2026-11-04)

**Normative baseline:** cardano-node 11.2.0 with the corrected forge trace order (ouroboros-consensus `4dd2ec9d4`, see [§8](#8-deviations-of-the-haskell-node)).

**Files:**
- [`schema/`](schema/): JSON Schema (draft 2020-12) for the envelope, the basic types, and each observable's payload. `observables.schema.json` validates one log line; it's generated by `tools/gen_observables.py`.
- [`examples/canonical.jsonl`](examples/): one real event per observable, in canonical form.
- [`tools/validate.py`](tools/validate.py): validates a log stream, reporting per namespace which events deviate and how. Requires the Python packages `jsonschema` and `referencing`:

  ```bash
  nix shell --impure --expr 'with import (builtins.getFlake "nixpkgs") {}; python3.withPackages (p: [ p.jsonschema ])' \
    -c python3 -I tools/validate.py schema <log.jsonl>
  ```

This document specifies the events a Cardano node implementation has to emit so that its performance can be analysed by the Cardano benchmarking workbench (`locli`), and compared to other implementations under identical workloads. It defines the *semantics* of each observable (the precise moment it marks, and what its payload means), and a canonical *syntax* for the parts that have to match exactly across implementations.

Implementations are not required to share the Haskell node's internal structure. An event name such as `Forge.Loop.ForgeTickedLedgerState` refers to a step that every Ouroboros Praos block producer performs; the specification describes that step, not the Haskell function that implements it.

The key words MUST, MUST NOT, SHOULD, SHOULD NOT and MAY are to be interpreted as described in RFC 2119.

## 1. Scope and conformance tiers

The catalogue covers the observables consumed by `locli` (the `interpreters` table in `bench/locli/src/Cardano/Unlog/LogObject.hs`), plus `ChainDB.AddBlockEvent.SwitchedToAFork`, which adopts blocks just as `AddedToCurrentChain` does.

Observables are grouped in tiers. An implementation claims conformance to a tier by emitting every observable of that tier, and of all lower tiers.

| Tier | Purpose | Observables |
|---|---|---|
| **1: Core** | Block production and diffusion across the cluster; resource usage. Required for any comparison. | `Resources` (portable fields); `Forge.Loop.StartLeadershipCheck`, `NodeIsLeader`, `NodeNotLeader`, `ForgedBlock`, `AdoptedBlock`; `ChainSync.Client.DownloadedHeader`; `BlockFetch.Client.SendFetchRequest`, `CompletedBlockFetch`; `ChainSync.ServerHeader.Update`; `BlockFetch.Server.SendBlock`; `ChainDB.AddBlockEvent.AddedToCurrentChain`, `SwitchedToAFork` |
| **2: Forging breakdown** | Where the time goes between leadership check and forged block. | `Forge.Loop.BlockContext`, `LedgerState`, `LedgerView`, `ForgeTickedLedgerState`, `ForgingMempoolSnapshot` |
| **3: Workload and ledger** | Transaction intake, mempool, ledger size, ledger snapshots. | `TxSubmission.TxInbound.Collected`, `Processed`; `Mempool.AddedTx`, `RemoveTxs`, `RejectedTx`; `LedgerMetrics`; `ChainDB.LedgerEvent.Snapshot.TookSnapshot` |
| **R: Runtime-specific** | Garbage-collected runtimes only; never compared across runtimes. | `Resources` GC fields (§5.1) |

Events not listed here MAY be emitted; consumers ignore them.

## 2. Log stream and envelope

### 2.1 Stream

- The log is a stream of **JSON lines**: UTF-8, one JSON object per line, terminated by `\n`.
- A stream MAY contain lines that aren't JSON objects (e.g. a start-up preamble on stdout). Consumers skip them; implementations SHOULD NOT emit them after the first event.
- Each node writes its own stream. A cluster run consists of one stream per node.

### 2.2 Envelope

Every event is an object with exactly these fields ([`schema/envelope.schema.json`](schema/envelope.schema.json)):

| Field | Type | Meaning |
|---|---|---|
| `at` | [Timestamp](#timestamp) | The moment the event occurred, taken **synchronously at the emission point**, not when the line is serialised or flushed. |
| `ns` | string | The event's namespace: dot-separated, case-sensitive, as listed in §5. |
| `sev` | `"Debug"` \| `"Info"` \| `"Notice"` \| `"Warning"` \| `"Error"` \| `"Critical"` | Severity. Informational; consumers don't rely on it. |
| `thread` | string | Opaque identifier of the emitting thread or task. |
| `host` | string | The node's name: unique within the cluster, constant for the run. |
| `data` | object | The payload, specified per observable in §5. |

Payload objects MAY contain fields beyond those specified (e.g. `kind`, a redundant event name the Haskell node always adds). Consumers ignore unknown fields. A field specified as *required* MUST be present, with the specified type and meaning.

## 3. Basic types

Formal definitions: [`schema/types.schema.json`](schema/types.schema.json).

#### Timestamp
RFC 3339 date-time in UTC, with the `Z` suffix, e.g. `"2026-09-07T13:00:57.002689231Z"`. Fractional seconds are mandatory; precision MUST be at least microseconds and SHOULD be nanoseconds. Trailing zeros of the fraction MAY be dropped.

#### SlotNo
JSON integer ≥ 0, the absolute slot number.

#### BlockNo
JSON integer ≥ 0, the block number (chain length): the first block of the chain has number 0. Never a string.

#### BlockHash
The block (header) hash: **64 lowercase hexadecimal characters**, the full 32-byte Blake2b-256 hash. Never truncated, and never prefixed (no `0x`).

Example: `"69eba3e8e082736b7b7670151945f81a8ce85cc8f2e911ae6f0bdbda39f5f6cb"`

Block hashes are the join key for all cross-node analysis: an event on node A and an event on node B refer to the same block if and only if their hashes are equal as strings. This is the most important syntactic requirement in this document.

#### ChainHash
A BlockHash, or the literal `"genesis"` where the referenced block is the genesis of the chain (e.g. the predecessor of the first block).

#### Point
A position on a chain: `"<BlockHash>@<SlotNo>"`, or the literal `"genesis"`.

Example: `"15e5c45cf0924a8cfb4307a4b35dcfc95bb177aaf52e314aefee964cf1ce102a@1556"`

#### TxId
A transaction ID: 64 lowercase hexadecimal characters, never truncated.

#### Duration
JSON number of **seconds** (fractional), ≥ 0.

#### Size
JSON integer ≥ 0, in **bytes**.

#### ConnectionId
A string of two endpoints separated by a single space: the local endpoint first, then the remote one. An endpoint is `host:port`; IPv6 addresses are written in brackets (`[::1]:3001`).

Example: `"172.31.94.226:30001 52.44.107.239:30049"`

Payloads carry it as `"peer": {"connectionId": <ConnectionId>}`. Benchmarks run on fixed topologies whose endpoints are known in advance, so a consumer maps endpoints to node names through the run's topology.

#### EdgeTiming
An operation that is traced on start and on completion is represented by two events of the same namespace, with this field:

- start: `{"edge": "Starting"}`
- completion: `{"edge": <Duration>}`, the operation's duration.

## 4. Emission requirements

These requirements apply to any configuration used for benchmarking. They aren't about syntax, but violating them silently corrupts the derived metrics.

1. **Completeness.** Events of tiers 1–3 MUST NOT be sampled, rate-limited, or dropped under load. Propagation metrics are computed per block and per node; one missing event removes that block's sample, or misattributes it.
2. **Full detail.** All BlockHash, Point and TxId values MUST be complete (§3). Where an implementation has configurable verbosity, benchmarking uses a level that yields complete values.
3. **Clock synchronisation.** Hosts MUST be NTP-synchronised. Cross-node propagation deltas are in the range of milliseconds; clock offsets between hosts directly add to them.
4. **Emission point.** Each event MUST be emitted at the point specified in §5, with `at` taken there. If an implementation buffers or writes logs asynchronously, the timestamp MUST still be taken synchronously at the emission point.
5. **Tracing cost.** Emitting an event SHOULD NOT block the code being measured (e.g. on I/O). In a benchmark, the cost of tracing becomes part of the measured performance.
6. **Resource sampling period.** `Resources` MUST be sampled every 1000 ms (±10%).

## 5. Observable catalogue

Each entry lists: namespace, tier, the precise emission point, required payload fields, and the metrics derived from it. Fields marked *opt.* are optional. Formal payload schemas: [`schema/observables.schema.json`](schema/observables.schema.json).

### 5.1 Resource sampling

#### `Resources` (tier 1; GC fields: tier R)

**Emitted:** periodically, every 1000 ms (§4), describing the node process.

| Field | Type | Kind | Meaning |
|---|---|---|---|
| `CentiCpu` | integer | cumulative | CPU time (user + system) since process start, in centiseconds |
| `RSS` | Size | gauge | Resident set size |
| `Threads` | integer | gauge | Number of OS threads |
| `FsRd`, `FsWr` | Size | cumulative | Bytes read from / written to storage since process start |
| `NetRd`, `NetWr` | Size | cumulative | Network bytes received / sent since process start. *opt.* |
| `CentiBlkIO` | integer | cumulative | Time spent waiting for block I/O, in centiseconds. *opt.* |
| `CentiMut` | integer | cumulative | **R:** CPU time spent in the mutator (application code), in centiseconds |
| `CentiGC` | integer | cumulative | **R:** CPU time spent in garbage collection, in centiseconds |
| `GcsMajor`, `GcsMinor` | integer | cumulative | **R:** Number of major / minor collections |
| `Alloc` | Size | cumulative | **R:** Bytes allocated on the managed heap |
| `Live` | Size | gauge | **R:** Live data on the managed heap, as measured by the most recent collection (major or minor) |
| `Heap` | Size | gauge | **R:** Memory currently in use by the managed heap, including fragmentation and free blocks |

Cumulative values are monotonically non-decreasing; consumers derive rates from differences between consecutive samples. Tier R fields are optional, and their meaning is specific to the runtime: comparing e.g. `Live` across a GHC node and a JVM node isn't meaningful. An implementation without a garbage-collected runtime omits them.

**Derived:** CPU, MUT and GC usage (% of one core); RSS, heap and live data; allocation rate; I/O rates; spans of sustained high CPU usage.

### 5.2 Forge loop

One iteration of the forge loop runs per slot on every block-producing node. All events of one iteration carry the same `slot`, the slot the iteration is for. Within an iteration they are emitted in the order of this section; an iteration ends early, without further events, when the node isn't leader or can't proceed.

#### `Forge.Loop.StartLeadershipCheck` (tier 1)

**Emitted:** at the start of the forge loop iteration for a slot, before any work for that slot.

| Field | Type | Meaning |
|---|---|---|
| `slot` | SlotNo | The slot of this iteration |

**Derived:** forge loop tardiness (delay after slot start); forge loop starts per slot.

#### `Forge.Loop.BlockContext` (tier 2)

**Emitted:** after determining the block the new block would extend (normally the tip of the current chain; its predecessor if the tip is already in this slot).

| Field | Type | Meaning |
|---|---|---|
| `slot` | SlotNo | The slot of this iteration |
| `blockNo` | BlockNo | The block number **of the block to be forged** (i.e. one more than that of the block it extends) |
| `prev` | Point | The point of the block it extends. *opt.* |

**Derived:** block context acquisition delay.

#### `Forge.Loop.LedgerState` (tier 2)

**Emitted:** after obtaining the ledger state at the point the new block would extend.

| Field | Type | Meaning |
|---|---|---|
| `slot` | SlotNo | The slot of this iteration |

**Derived:** ledger state acquisition delay.

#### `Forge.Loop.LedgerView` (tier 2)

**Emitted:** after obtaining the ledger view (the protocol-relevant projection of the ledger state, e.g. stake distribution) forecast for the current slot.

| Field | Type | Meaning |
|---|---|---|
| `slot` | SlotNo | The slot of this iteration |

**Derived:** ledger view acquisition delay.

#### `Forge.Loop.NodeIsLeader` / `Forge.Loop.NodeNotLeader` (tier 1)

**Emitted:** when the leadership check for the slot concludes. Exactly one of the two per iteration that reaches the check. After `NodeNotLeader` the iteration ends.

| Field | Type | Meaning |
|---|---|---|
| `slot` | SlotNo | The slot of this iteration |

**Derived:** leadership check duration; leadership count per node.

#### `Forge.Loop.ForgeTickedLedgerState` (tier 2)

**Emitted:** after the ledger state has been ticked (advanced to the current slot, applying any time-based transitions such as epoch boundary processing), and the result fully evaluated. Only emitted when leader.

| Field | Type | Meaning |
|---|---|---|
| `slot` | SlotNo | The slot of this iteration |
| `prev` | Point | The point of the block the new block extends. *opt.* |

**Derived:** ledger ticking duration (from `NodeIsLeader`).

#### `Forge.Loop.ForgingMempoolSnapshot` (tier 2)

**Emitted:** after the mempool snapshot consistent with the ticked ledger state has been obtained **and the transactions for the new block have been selected from it**. The interval from `ForgeTickedLedgerState` to this event covers all mempool work for the block. Only emitted when leader.

| Field | Type | Meaning |
|---|---|---|
| `slot` | SlotNo | The slot of this iteration |
| `prev` | Point | The point of the block the new block extends. *opt.* |
| `mempoolHash` | ChainHash | The point the mempool was last synchronised to: its hash. *opt.* |
| `mempoolSlot` | SlotNo | The point the mempool was last synchronised to: its slot. *opt.* |

**Derived:** mempool snapshot duration.

#### `Forge.Loop.ForgedBlock` (tier 1)

**Emitted:** after the new block has been constructed and signed, before it's submitted to chain selection.

| Field | Type | Meaning |
|---|---|---|
| `slot` | SlotNo | The slot of this iteration (= the block's slot) |
| `block` | BlockHash | The new block |
| `blockNo` | BlockNo | The new block's number |
| `blockPrev` | ChainHash | The hash of the block it extends |

**Derived:** forging duration; blocks forged per node; the root of every per-block propagation measurement.

#### `Forge.Loop.AdoptedBlock` (tier 1)

**Emitted:** after chain selection has processed the node's own new block, and it has become the tip of the node's chain.

| Field | Type | Meaning |
|---|---|---|
| `slot` | SlotNo | The slot of this iteration |
| `blockHash` | BlockHash | The adopted block |
| `blockSize` | Size | The block's size |

**Derived:** forged-to-self-adopted delay; block size.

### 5.3 Block diffusion

These events are emitted per peer connection, on both the downstream (receiving) and upstream (forwarding) side. Every block forged in the cluster is expected to produce, on each other node, the sequence `DownloadedHeader` → `SendFetchRequest` → `CompletedBlockFetch` → adoption, unless the block is superseded first.

#### `ChainSync.Client.DownloadedHeader` (tier 1)

**Emitted:** when a header has been received from an upstream peer while following its chain (roll forward), before the header is validated.

| Field | Type | Meaning |
|---|---|---|
| `block` | BlockHash | The header's block |
| `blockNo` | BlockNo | The block's number |
| `slot` | SlotNo | The block's slot |
| `peer` | `{connectionId}` | The upstream peer. *opt.* |

A node receives the same header from several peers; consumers use the first occurrence per block.

**Derived:** first peer notice (delay after the block's slot start).

#### `BlockFetch.Client.SendFetchRequest` (tier 1)

**Emitted:** when a request for a range of block bodies is actually sent over the wire to a peer.

| Field | Type | Meaning |
|---|---|---|
| `head` | ChainHash | The newest block of the requested range |
| `length` | integer ≥ 1 | The number of blocks in the requested range |
| `peer` | `{connectionId}` | The peer the request was sent to. *opt.* |

**Derived:** notice-to-fetch-request delay.

#### `BlockFetch.Client.CompletedBlockFetch` (tier 1)

**Emitted:** when one block body has been completely received and decoded (within a range request, once per block).

| Field | Type | Meaning |
|---|---|---|
| `block` | BlockHash | The received block |
| `size` | Size | The block's size. *opt.* |
| `delay` | Duration | Time from the start of the block's slot (according to its header) until it was received. *opt.* |
| `peer` | `{connectionId}` | The peer it was received from. *opt.* |

**Derived:** fetch duration; first peer fetch.

#### `ChainSync.ServerHeader.Update` (tier 1)

**Emitted:** when the chain-sync server has obtained the next chain update for a downstream peer, immediately before sending it. For this specification, only **roll-forward instructions** are relevant: they announce a header to the peer.

| Field | Type | Meaning |
|---|---|---|
| `addBlock` | Point | The point of the header announced (roll forward). Present iff this is a roll-forward. |
| `rollBackTo` | Point | The point rolled back to. Present iff this is a rollback. |
| `blockingRead` | boolean | `true` if the peer was already following at the tip, so the server had to wait for the chain to change: the update is a newly adopted block. `false` if the update was available immediately (the peer is catching up). |
| `risingEdge` | boolean | `true` on the event emitted before sending. *opt.:* the Haskell node additionally emits a second event for the same update after the message has been sent, without this field; consumers ignore it. |
| `peer` | `{connectionId}` | The downstream peer. *opt.* |

A header announcement is an event with `addBlock` present, `blockingRead: true` and `risingEdge: true`. The announced block is the hash part of `addBlock`.

**Derived:** forged-to-announced, fetched-to-announced, slot-start-to-announced.

#### `BlockFetch.Server.SendBlock` (tier 1)

**Emitted:** when the block-fetch server starts sending a block body to a downstream peer.

| Field | Type | Meaning |
|---|---|---|
| `block` | ChainHash | The block being sent |
| `peer` | `{connectionId}` | The downstream peer. *opt.* |

**Derived:** forged-to-sending, fetched-to-sending.

### 5.4 Chain selection

#### `ChainDB.AddBlockEvent.AddedToCurrentChain` (tier 1)

**Emitted:** when chain selection has extended the node's current chain with one or more blocks, and the new chain has become current.

| Field | Type | Meaning |
|---|---|---|
| `newtip` | Point | The tip of the new current chain |

**Derived:** fetched-to-adopted; end-to-end propagation (time from slot start until a given fraction of the cluster has adopted the block).

#### `ChainDB.AddBlockEvent.SwitchedToAFork` (tier 1)

**Emitted:** when chain selection has replaced the node's current chain with a fork that's preferable, and the fork has become current.

| Field | Type | Meaning |
|---|---|---|
| `newtip` | Point | The tip of the new current chain |

**Derived:** as `AddedToCurrentChain`: the block at `newtip` is adopted at this moment. Also: fork switches per node.

### 5.5 Ledger

#### `ChainDB.LedgerEvent.Snapshot.TookSnapshot` (tier 3)

**Emitted:** twice per ledger snapshot written to disk: when writing starts, and when the snapshot has been completely written.

| Field | Type | Meaning |
|---|---|---|
| `enclosedTime` | EdgeTiming | Start (`{"edge": "Starting"}`), or completion with the writing duration |
| `tip` | Point | The point of the ledger state being written. *opt.* |

**Derived:** snapshot count; mean and maximum snapshot duration; windows of snapshot writing (for correlating resource usage).

#### `LedgerMetrics` (tier 3)

**Emitted:** periodically; for benchmarking, once per slot, about 700 ms after the slot start.

| Field | Type | Meaning |
|---|---|---|
| `slot` | SlotNo | The slot it was taken in |
| `utxoSize` | integer | Number of entries in the UTxO set |
| `chainDensity` | number | Density of the current chain's volatile part (blocks per slot over the most recent *k* blocks) |
| `delegMapSize` | integer | Number of stake delegations. *opt.* |

**Derived:** UTxO set size; chain density.

### 5.6 Transaction intake and mempool

#### `TxSubmission.TxInbound.Collected` (tier 3)

**Emitted:** by the inbound transaction-submission handler of one peer connection, when a batch of transactions received from that peer is about to be submitted to the mempool.

| Field | Type | Meaning |
|---|---|---|
| `count` | integer ≥ 0 | Number of transactions in the batch being submitted |
| `peer` | `{connectionId}` | The peer |

The batch is what's submitted, which isn't necessarily what was received last: an implementation may buffer received transactions and submit them later (e.g. to preserve the order in which the peer announced them).

#### `TxSubmission.TxInbound.Processed` (tier 3)

**Emitted:** when the mempool has finished processing the batch announced by the preceding `Collected` on the same peer connection.

| Field | Type | Meaning |
|---|---|---|
| `accepted` | integer ≥ 0 | Transactions added to the mempool |
| `rejected` | integer ≥ 0 | Transactions not added: invalid, **or already known** (in the mempool or on chain) |
| `peer` | `{connectionId}` | The peer |

Per peer connection, `Collected` and `Processed` strictly alternate, and `accepted + rejected` equals the preceding `count`. Consumers pair them by `peer`.

**Derived:** transaction processing time per batch; accepted and rejected totals; reject ratio (which explains differences between raw and per-transaction CPU usage); CPU per processed transaction.

#### `Mempool.AddedTx` (tier 3)

**Emitted:** after a valid transaction has been added to the mempool.

| Field | Type | Meaning |
|---|---|---|
| `mempoolSize` | `{numTxs, bytes}` | The mempool's size after the addition: number of transactions and total Size |
| `tx` | `{txid}` | The transaction's TxId. *opt.* |

#### `Mempool.RemoveTxs` (tier 3)

**Emitted:** after transactions have been removed from the mempool because they're no longer valid against the ledger state (e.g. included in an adopted block, or conflicting with one).

| Field | Type | Meaning |
|---|---|---|
| `mempoolSize` | `{numTxs, bytes}` | The mempool's size after the removal |
| `txs` | array of `{tx: {txid}}` | The removed transactions. *opt.* |

#### `Mempool.RejectedTx` (tier 3)

**Emitted:** when a transaction has been rejected by mempool validation.

| Field | Type | Meaning |
|---|---|---|
| `mempoolSize` | `{numTxs, bytes}` | The mempool's size (unchanged). *opt.* |
| `tx` | `{txid}` | The transaction's TxId. *opt.* |

**Derived (mempool):** mempool occupancy over time; rejection count.

## 6. Ordering invariants

For each node, ordered by `at`. These can be checked mechanically on any log; a violation indicates a wrong emission point.

**Forge loop**, per slot *s*:
1. `StartLeadershipCheck` ≤ `BlockContext` ≤ `LedgerState` ≤ `LedgerView` ≤ (`NodeIsLeader` | `NodeNotLeader`).
2. If `NodeIsLeader`: `NodeIsLeader` ≤ `ForgeTickedLedgerState` ≤ `ForgingMempoolSnapshot` ≤ `ForgedBlock` ≤ `AdoptedBlock` (unless the block isn't adopted).
3. `StartLeadershipCheck` for *s* is emitted no earlier than the start of slot *s*.

**Per block** *b*, on a node that didn't forge it:
1. `DownloadedHeader(b)` ≤ `SendFetchRequest` (range containing *b*) ≤ `CompletedBlockFetch(b)` ≤ adoption of *b* (`AddedToCurrentChain` or `SwitchedToAFork` with *b* on the new chain).
2. Forwarding of *b* (`ServerHeader.Update` announcing *b*, `Server.SendBlock(b)`) happens after `CompletedBlockFetch(b)`. The header MAY be announced before adoption.

**Per block** *b*, on the node that forged it: `ForgedBlock(b)` ≤ announcement of *b* and `Server.SendBlock(b)`.

**Per peer connection:** `Collected` and `Processed` strictly alternate, starting with `Collected`.

**Snapshots:** `TookSnapshot` start and completion events strictly alternate per node.

## 7. Derived metrics

The metrics in the workbench reports, and the observables they're computed from. Δ(A, B) is the time from event A to event B on the same node, for the same slot or block.

| Metric | Computed as |
|---|---|
| Forge loop tardiness | Δ(slot start, `StartLeadershipCheck`) |
| Block context / ledger state / ledger view acquisition | Δ between consecutive forge loop events (§5.2) |
| Leadership check duration | Δ(`LedgerView`, `NodeIsLeader` \| `NodeNotLeader`) |
| Ledger ticking | Δ(`NodeIsLeader`, `ForgeTickedLedgerState`) |
| Mempool snapshotting | Δ(`ForgeTickedLedgerState`, `ForgingMempoolSnapshot`) |
| Leadership to forged | Δ(`ForgingMempoolSnapshot`, `ForgedBlock`) |
| Forged to announced / sending / self-adopted | Δ(`ForgedBlock`, first `ServerHeader.Update` announcing the block / first `Server.SendBlock` / `AdoptedBlock`) |
| First peer notice / fetch | Δ(slot start, first `DownloadedHeader` / `CompletedBlockFetch` for the block on the fastest peer) |
| Notice to fetch request | Δ(`DownloadedHeader`, `SendFetchRequest`) |
| Fetch duration | Δ(`SendFetchRequest`, `CompletedBlockFetch`) |
| Fetched to announced / sending / adopted | Δ(`CompletedBlockFetch`, announcement / `Server.SendBlock` / adoption) |
| End-to-end propagation *p* | Δ(slot start, adoption of the block by fraction *p* of the cluster's nodes) |
| Resource usage | `Resources` differences per sample (§5.1) |

Slot start is computed from the genesis parameters (system start and slot length); it's not an event.

## 8. Deviations of the Haskell node

What the Haskell cardano-node emits differs from this specification in the following places. Implementations SHOULD follow the specification, not the deviation. Consumers of Haskell node logs have to accept the deviating form.

### 8.1 Syntax

| # | Where | Haskell node emits | Specification |
|---|---|---|---|
| S1 | Point at genesis, e.g. `BlockContext.tip`, `ServerHeader.Update.rollBackTo` | `"genesis (origin)"` | `"genesis"` |
| S2 | `TookSnapshot.tip` | Haskell `show` output: `"RealPoint (SlotNo 981) 4c9e24c2…"` | Point: `"4c9e24c2…@981"` |
| S3 | ChainHash at genesis: `ForgedBlock.blockPrev`, `SendFetchRequest.head`, `Server.SendBlock.block`, `ForgingMempoolSnapshot.mempoolHash` | `"GenesisHash"` | `"genesis"` |
| S4 | ChainHash at genesis: `CompletedBlockFetch.block` | `"Genesis"` | `"genesis"` |
| S5 | `BlockContext`: slot | key `"current slot"` (contains a space) | key `slot` |
| S6 | `BlockContext`: number of the block to be forged | key `"tipBlockNo"`, and the node's own documentation describes it as the number of the block extended, i.e. one less, which is wrong | key `blockNo`, the number of the block to be forged |
| S7 | `BlockContext`: point extended | key `tip` | key `prev`, as in `ForgeTickedLedgerState` |
| S8 | TxId in `Mempool.*` events | truncated to 8 hex characters (`"a2f68ff4"`) | full TxId |
| S9 | `ServerHeader.Update.tip` (not consumed) | `{"block":"genesis","blockNo":-1,"slot":0}` at genesis | not specified |
| S10 | At detail level `DMinimal` | BlockHash truncated to 7 characters | always complete (§4.2) |
| S11 | `TookSnapshot.enclosedTime`, node ≤ 11.1 | `{"tag":"RisingEdge"}` / `{"tag":"FallingEdgeWith","contents":<secs>}` | EdgeTiming |
| S12 | `Resources.RSS` | page count × 4096, regardless of the actual page size | bytes |

### 8.2 Semantics and completeness

| # | Haskell node behaviour | Specification |
|---|---|---|
| E1 | **11.2.0 as released** emits `ForgingMempoolSnapshot` *before* selecting the transactions for the block, so mempool work is attributed to "Leadership to forged" instead of "Mempool snapshotting". Fixed in ouroboros-consensus `4dd2ec9d4`; 11.1.x and earlier emit it after. | Emitted after transaction selection (§5.2). |
| E2 | `AddedToCurrentChain` events that carry no ledger events are rate-limited to about 1.25 events per second (a budget-based limiter: short bursts pass, sustained higher rates are thinned). The limiter is set up in code (`withAddedToCurrentChainEmptyLimited`, `cardano-node/src/Cardano/Node/Tracing/Tracers/ChainDB.hs`), not in the configuration, because it applies only to the events *without* ledger events, which a namespace-based limiter can't select. It reproduces the eliding tracer of the legacy logging system, though with the value inverted: the legacy code reported at most once per 1250 ms (0.8 events per second), while `limitFrequency` takes messages per second. It keeps chain sync from flooding the log with one event per adopted block. The suppressed events are exactly the ones adoption is measured from. Irrelevant at steady-state benchmark block rates, but bursts (catching up, fork switches) lose adoption timestamps, a violation of §4.1. | Never limited. Making it configurable would need its own namespace for the events without ledger events. |
| E3 | The shipped configurations limit `BlockFetch.Client.CompletedBlockFetch` to 2 events per second (`maxFrequency`). | Never limited (§4.1); remove the limiter for benchmarking at high block rates. |
| E4 | `TxInbound.Collected`/`Processed` are correlated by `locli` through the envelope's `thread`, which works because the Haskell node runs one inbound handler thread per peer. | Correlated by `peer` (§5.6). |
| E5 | Severity is `Debug` for several required events (`BlockContext`, `LedgerState`, `LedgerView`, `ForgeTickedLedgerState`, `ForgingMempoolSnapshot`, `TxInbound.*`); a default configuration filters them out. The workbench configuration enables them. | Severity is informational (§2.2); required events are always emitted for benchmarking. |
| E6 | `TxInbound.Collected.count` is the number of transactions in the peer's latest reply, but the batch submitted to the mempool is the transactions that can be acknowledged in order, which may include transactions buffered from earlier replies. `Processed.rejected` is computed as `count − accepted` instead of being counted, so it's wrong whenever the two batches differ, and **negative** when more is submitted than was received (389 of 6,755 events in a 20-hour node log). `accepted` is correct. The correct rejected count is available in the node as the length of the list traced by `TxSubmission.TxInbound.RejectedFromMempool`. | `count` is the size of the submitted batch, and `accepted + rejected = count` (§5.6). |

### 8.3 Documentation gaps

The node's own trace documentation (`cardano-node trace-documentation`, 11.2.0) has **no description** for `Forge.Loop.ForgeTickedLedgerState`, `Forge.Loop.ForgingMempoolSnapshot`, `BlockFetch.Client.CompletedBlockFetch` and `Resources`. Their semantics in this document were established from the source (ouroboros-consensus `NodeKernel/Forge.hs`, `hermod-trace-resources`). The description of `Forge.Loop.ForgedBlock` mentions the mempool size at forging time, which the payload doesn't contain; the description of `Forge.Loop.BlockContext` gets the block number wrong (S6).

## 9. Open questions

1. **Leios.** Leios introduces new observables (endorser blocks, votes, certificates), and changes what "adoption" means. A future version of this specification extends the catalogue once the Leios traces are stable.
2. **Versioned schemata.** Currently there's one schema, and supporting it is all an implementation needs for its performance to be analysed. Once the catalogue evolves (e.g. for Leios), the schema becomes versioned: a stream would then declare the version it conforms to (e.g. in a start-up event), so consumers can select the matching schema, and the documented deviations of a given implementation version.
