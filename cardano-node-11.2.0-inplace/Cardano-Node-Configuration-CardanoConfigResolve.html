Description

Turning a node configuration file into the node's NodeConfiguration, with whichever of the two parsers the file is written for.

The node understands two configuration dialects while the migration to the shared cardano-config package is in progress:

Legacy
the flat, pre-cardano-config configuration the node has always read with its own POM parser. Both parsers can read it (cardano-config migrates it on the fly, see migrate), so it is resolved with both and the results are compared: the POM result is what the node runs on, and every divergence is reported as a non-fatal warning so the two can be reconciled before POM is dropped.
Envelope
the cardano-config { $schema, Version, Configuration } envelope. The POM parser cannot read it at all (every setting lives nested under Configuration, so POM sees an empty document and fails on the first required field), so it is not run: cardano-config alone resolves the configuration and the adapter maps it to the node's NodeConfiguration.

The dialect is decided by classifyConfigurationFile, on the file itself.

Note that the legacy path pays for the second parse at every startup: cardano-config reads and decodes the era genesis files as part of resolving, so the genesis files are parsed twice. That is the price of the cross-check and it goes away with the POM parser.

classifyConfigurationFile :: FilePath -> IO ConfigurationDialect Source #

Decide which dialect a configuration file is written in.

The marker is the envelope's Configuration key: that is exactly what cardano-config splits the document on (splitEnvelope), and exactly what makes the document unreadable to POM (which expects the settings at the top level). A file that cannot even be decoded as YAML is reported as legacy so that the POM path raises the syntax error, as it always did.

tracingConfigSource :: FilePath -> IO ConfigSource Source #

How to hand a node configuration file's tracing settings to trace-dispatcher, for a tool with a file and no node to resolve it.

Reading a file, the library expects the tracing settings at its root. An envelope puts them at Configuration.HermodTracing, so hand over that object instead, which is what FromJSONObject is for. Anything else goes as the file, as before.

Command-line layers

nodeCliPartialConfiguration :: FilePath -> IO (Maybe PartialNodeConfiguration, [String]) Source #

Re-parse the node's own command line with cardano-config's CLI parser, so both parsers resolve from the same file + CLI inputs.

The node is invoked as cardano-node run <flags…> (the RTS has already stripped its own arguments), so the leading non-flag subcommand token is dropped to get the flag list; cardano-config's parseCliArgs is a flat parser with no run subcommand, matching that stripped list. On failure the returned message leads with actionable guidance for each offending flag. | The node's own command-line layer for the configuration being resolved: the flags this process was given, parsed with the node's own run parser.

This is the POM twin of cardanoConfigCliArgs: the two read the SAME flags, each with its own parser, which is what makes a comparison of the two resolved configurations a comparison of the parsers rather than of their inputs.

nodeCliLayer :: FilePath -> [String] -> (Maybe PartialNodeConfiguration, [String]) Source #

The node's command-line layer for a given flag list, as nodeRunParser reads it. Pure, so a caller that is not the node's own process (a test, say) can ask for the layer of a stated command line.

An empty flag list is not the same as no layer: the node's parser supplies CLI defaults of its own, and an absent --shutdown-on-slot-synced resolves to NoShutdown rather than to "unset".

Returns the layer together with any line to report. A flag the node's parser rejects is not fatal: the layer falls back to the flagless one and the rejection is reported, so the rest is still compared. Nothing means there is no layer to apply at all, which the caller reports and continues without.

cardanoConfigCliLayer :: FilePath -> [String] -> Either String CliArgs Source #

cardano-config's command-line layer for a given flag list, as its own parser reads it. The twin of nodeCliLayer, and pure for the same reason: a caller that is not the node's own process can ask for the layer of a stated command line, and the two parsers can then be given the same one.
